# HP LaserJet 1020 macOS Printing Solution — Implementation Specification

## Problem Statement

The reference printer depends on host-side firmware and raster processing that current macOS does not provide. The project needs one implementation handoff that preserves the standard macOS printing experience, defines honest support claims, and makes the personal-use installation reproducible and recoverable without redistributing proprietary firmware or reopening settled architecture decisions.

## Solution

Build a local, user-space IPP Printer Application in C using PAPPL 1.4.12, libusb, and a pinned source adaptation of the `foo2zjs` ZjStream/JBIG encoder. Install it for personal use as an administrator-installed legacy LaunchDaemon whose provider runs under a dedicated unprivileged account, exposes IPP only on loopback, accepts validated user-supplied firmware, and is governed by the lifecycle, release, evidence, and privacy contracts below.

## User Stories

1. As the owner of the reference printer, I want it available in Printers & Scanners, so that I can print through normal macOS applications.
2. As a local non-administrator, I want to submit jobs to the installed queue, so that printing is not tied to the installing account.
3. As the project owner, I want ordinary monochrome documents to work through both connection paths, so that a support claim reflects the intended hardware setup.
4. As the project owner, I want unsupported connection paths to remain visibly unverified, so that one dock success is not misrepresented as general compatibility.
5. As a user, I want the service to recognize a powered-on printer that lacks firmware, so that the next job waits safely instead of failing mysteriously.
6. As a user, I want firmware uploaded once per power cycle and verified before printing, so that jobs never reach an uninitialized device.
7. As a rights holder, I want HP firmware excluded from project artifacts, so that the project does not redistribute proprietary material.
8. As a user, I want a clear firmware-required state and exact recovery action, so that a valid installation is not mistaken for a failed one.
9. As a user, I want cancellation and disconnect outcomes to reflect whether bytes reached the printer, so that automatic retry cannot duplicate pages.
10. As a user, I want media faults to be recoverable without reinstalling or restarting the service, so that routine printer conditions stay routine.
11. As a user, I want incorrect raster resolution mappings rejected or normalized, so that output cannot silently print at the wrong physical size.
12. As a project owner, I want bounded local logs and explicit diagnostic bundles, so that failures are actionable without telemetry.
13. As a privacy-conscious user, I want diagnostics to exclude print contents, filenames, identities, credentials, and firmware, so that support evidence does not leak sensitive data.
14. As an administrator, I want installation to converge from partial product state, so that an interrupted attempt has one safe recovery path.
15. As an administrator, I want disable to preserve product data, so that I can stop integration without uninstalling.
16. As an administrator, I want uninstall to preview and remove only product-owned artifacts, so that unrelated queues and system printing components remain intact.
17. As an administrator, I want incomplete removal to report residue precisely, so that the product never claims a clean state falsely.
18. As a maintainer, I want updates staged and health-checked before activation, so that a failed replacement restores the prior validated payload.
19. As a maintainer, I want active jobs protected during updates, so that deployment does not corrupt or lose in-flight work.
20. As a maintainer, I want every dependency and patch content-addressed, so that builds do not drift with upstream state.
21. As a maintainer, I want release builds to reject dirty or unrecorded inputs, so that a personal release is reconstructable from its record.
22. As a maintainer, I want hosted checks to run without firmware or release secrets, so that CI cannot become a proprietary-content or credential channel.
23. As a maintainer, I want a tagged source revision tied to sealed local evidence, so that the installed personal release has a precise identity.
24. As a maintainer, I want failed validation runs retained immutably but excluded from successful release records, so that evidence is honest and auditable.
25. As a maintainer, I want capability results separate from normative policy, so that new observations do not silently amend the specification.
26. As a maintainer, I want every support claim backed by immutable passing scenarios, so that “verified” has a mechanical meaning.
27. As a maintainer, I want evidence invalidated by affected scope after code, dependency, or macOS changes, so that stale results cannot authorize a release.
28. As a maintainer, I want static conformance checks to reject broken requirement and schema references, so that downstream issues can safely cite stable IDs.
29. As an implementer, I want narrow, typed component contracts and host test doubles, so that device behavior can be developed without hardware.
30. As a future distributor, I want the personal layout to preserve a signed and notarized path, so that public distribution can be added by an explicit later decision rather than a rewrite.

## Implementation Decisions

### 1. Purpose, scope, audience, and conformance

This document is the sole normative prose entry point for implementation. The companion artifacts in section 5 are normative only for their machine-consumed contracts. Mutable observations remain outside this document.

The terms `MUST`, `MUST NOT`, `SHOULD`, and `MAY` are normative keywords. A conforming implementation satisfies every `REQUIRED` requirement at the applicable cumulative milestone. An `EVIDENCE GAP` is mandatory work whose support claim remains blocked until accepted evidence exists. A `DEFERRED` requirement applies only at its named future boundary. Retired requirement IDs remain reserved and are never reused.

Milestones are `BASIC` (basic printing milestone), `PERSONAL` (first personal release), `CAPABILITY` (verified capability envelope), and `PUBLIC` (deferred public binary release). `PERSONAL` inherits `BASIC`; `CAPABILITY` inherits both. Verification classes are `STATIC`, `HOST`, `REFERENCE_MAC`, `REFERENCE_PRINTER`, `HUMAN_REVIEW`, and `RELEASE_RECORD`. Coverage IDs name scenarios rather than mutable results.

### 2. Domain terms and fixed support boundary

Domain terms have the meanings in `CONTEXT.md`. In particular, a clean product state means absence of product-owned artifacts, not a fresh operating-system installation; a personal release is a tagged source revision plus retained local evidence, not a downloadable binary; and a verified capability envelope contains only behaviors accepted under the validation contract.

Non-normative observation: the dock path, unprivileged USB claim, pre-firmware identity `03f0:2b17`, standard queue submission, and clean full-size A4 output have prototype evidence. The direct adapter path, post-firmware descriptor behavior across both paths, and complete production capability envelope do not yet have accepted release evidence.

## Testing Decisions

The highest reusable seam is the repository-level specification conformance command. It parses this document and the schema catalog in one host-only run. Good tests assert externally visible acceptance or rejection of a complete artifact, not parser internals.

- Run `python3 scripts/check_implementation_spec.py` for the current repository.
- Run `python3 -m unittest discover -s tests -p 'test_spec_checks.py'` for negative fixtures covering duplicate IDs, missing fields, broken decisions, unknown schemas, missing coverage, and unknown requirement references.
- Component work uses the host test doubles required by COMP-008; printer behavior and physical output remain at the reference-printer seam.
- Existing prior art is the end-to-end printing prototype for the raster and USB evidence chain and the service-launch-boundary wizard for whole-host lifecycle behavior. Prototype implementation details are not asserted by production tests.
- A good lifecycle test begins at a named state, invokes a public operation or safe physical trigger, and asserts the resulting state, retained data, observable status, and retry rule from the relevant transition row.

## Out of Scope

Production implementation, source-tree decomposition, function-level design, backlog regeneration or reordering, current test outcomes, support claims without accepted evidence, printer models other than the reference printer, Intel Macs, network or mobile printing, a custom GUI, telemetry, kernel extensions, deliberate paper jams, App Store distribution, and operation of a public binary release channel are outside this specification task.

Any substantive amendment needs a reviewed decision reference; editorial corrections do not.
