# macOS 26 packaging and service lifecycle

Research date: 2026-08-27. Scope: public, non-Mac-App-Store distribution of a background printing service on macOS 26. Sources are Apple documentation only.

## Decision-ready summary

For the normal Gatekeeper-approved path, ship a flat installer package. Sign every executable with Developer ID Application, sign the package with Developer ID Installer, enable hardened runtime and secure timestamps, notarize with `notarytool`, and staple the ticket. For the service, use the macOS 13+ `SMAppService` bundle layout and make the background item visible and disableable in System Settings. A signed, explicit uninstaller is part of the product because macOS 26 has no general reverse operation for a consumer `.pkg` install.

A conservative first-release design is: install one signed, GUI-less provider app under `/Library/Application Support/<vendor>/`; embed its daemon plist in `Contents/Library/LaunchDaemons`; register it through `SMAppService`; keep any root process narrowly scoped; distribute updates as replacement packages; use unified logging without print-job content; and unregister the service before deleting product-owned files.

## Hard platform requirements and behavior

These are requirements for the intended frictionless public-distribution path, not a claim that macOS makes it impossible for a user to override Gatekeeper and run unsigned software.

| Area | Platform fact | Consequence |
| --- | --- | --- |
| Distribution identity | Public Developer ID distribution requires Apple Developer Program membership. Executables and bundles use **Developer ID Application**; an independently distributed installer package uses **Developer ID Installer**. A package is the best-supported container when a product has a daemon, multiple components, protected install locations, or installation scripts. | Sign every code object, nested code first, then sign the flat `.pkg`. Do not use an application certificate to sign the package or an installer certificate to sign Mach-O code. ([Developer ID](https://developer.apple.com/support/developer-id/), [packaging Mac software](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution), [distribution signing](https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/)) |

Current submissions use `notarytool`, not `altool`. | Treat signing and notarization as release gates for the daemon, any controller/uninstaller/updater, and the package. Hardened-runtime exceptions should be explicit and minimal. ([notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues)) |
| Ticket delivery | Gatekeeper can retrieve a successful notarization ticket online. Stapling attaches it to an app, disk image, or flat package so Gatekeeper can validate it offline. | Stapling is not logically necessary when the ticket is reachable, but it is operationally necessary for reliable offline installation; staple and validate the artifact actually distributed. ([custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)) |
| Sandbox | App Sandbox is mandatory for Mac App Store apps but optional for directly distributed notarized apps. Hardened runtime remains mandatory for notarization. Authorization Services is unavailable inside App Sandbox. | Do not add App Sandbox merely as a packaging requirement. Decide it component by component after the printing and privilege model is known. ([preparing an app for distribution](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution), [Authorization Services](https://developer.apple.com/documentation/security/authorization-services)) |
| Certificate expiry | A Developer ID-signed app whose certificate was valid when signed can still install after certificate expiry, but a package runs only while its Developer ID Installer certificate is valid. Revocation is stricter. | Re-sign downloadable historical packages before the installer certificate expires, and use a new valid certificate for every new release. ([Developer ID certificate behavior](https://developer.apple.com/support/developer-id/)) |
| Background-service layout | On macOS 13+, `SMAppService` is the current API for login items, launch agents, and launch daemons. A daemon plist belongs in the provider app at `Contents/Library/LaunchDaemons`; its program is inside the signed bundle and referenced with `BundleProgram`. Bundle-contained metadata is protected by the app signature and is attributed to the provider in Login Items. | For a macOS 26-only design, make `SMAppService` the default rather than installing a loose plist and executable. ([updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), [Apple’s GUI-less package sample](https://developer.apple.com/documentation/servicemanagement/updating-your-app-package-installer-to-use-the-new-service-management-api)) |
| Approval and user control | `SMAppService.register()` registers subject to user approval. A launch daemon does not bootstrap until an administrator approves it, then bootstraps on future boots. The user can later disable the item in System Settings. Software is expected to check status and behave sensibly while disabled. | Installation success and service activation are distinct states. Surface purpose and status clearly; do not silently re-enable an item the user disabled. ([`register()`](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29), [managing ongoing background processes](https://developer.apple.com/documentation/appkit/managing-ongoing-background-processes-in-your-mac)) |
| Execution context | A LaunchDaemon is system-wide, may run before login, has no UI, and runs as root under the Service Management model. A LaunchAgent runs in a logged-in user’s context. Apple’s security guidance requires least privilege and minimizing root code. | Root is an architecture choice forced only by the operations that actually need it, not by “background printing” as a label. UI and user interaction cannot live in the daemon. ([Service Management](https://developer.apple.com/documentation/servicemanagement/), [elevating privileges safely](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/Articles/AccessControl.html)) |

([macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes)) |

## Security and lifecycle design choices

### Service placement, account, and authorization

- Use Apple’s GUI-less package pattern: a signed provider `.app` under `/Library/Application Support/<vendor>/`, containing the executable and launchd plist. This path is a supported example, not a mandated literal location.
- Keep privileged operations as a small closed API. A privileged helper must authenticate its client by code identity, validate every request and path, and never execute a caller-supplied command or mutable payload. Apple explicitly says both sides of a privilege boundary are untrusted. ([designing secure helpers and daemons](https://developer.apple.com/library/archive/documentation/Security/Conceptual/SecureCodingGuide/DesigningSecureHelpers/DesigningSecureHelpers.html), [code-signing requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements))
- If printer access works without root, prefer a user-context agent or a small nonprivileged process. If only a narrow setup/device operation needs root, isolate that operation rather than running rendering, network update, parsing, or UI code as root. Apple does not require a product-specific Unix account; its older security guidance recommends a locally unique account when a daemon starts privileged and drops privileges. This needs prototype validation against the actual USB/CUPS access path.
- Expect both installer authorization for protected writes and Background Items approval for the daemon. The exact sequence for a GUI-less package should be verified on a clean macOS 26 VM; Apple documents the states but not one universal installer UX.

### Updates

- Outside the Mac App Store, software updates are developer-managed; Apple does not require a particular updater. The smallest safe first release is a newly signed, notarized replacement `.pkg` installed by Installer. ([macOS distribution](https://developer.apple.com/macos/distribution/))
- Preserve Team ID, bundle identifiers, and designated requirements across versions. macOS uses the designated requirement to recognize new versions as the same code, including continuity of privacy decisions. ([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements))
- If an automatic updater is added, download unprivileged where possible, use HTTPS, validate the complete signature and expected signer before crossing the privilege boundary, and enforce version/downgrade policy. Installer validates package integrity; product release policy is still the updater’s responsibility.
- Never patch signed code in place. Use Installer/`installer`, or write a new file and atomically replace the old one; macOS caches code-signature state and in-place mutation can cause `Code Signature Invalid` crashes. ([updating Mac software](https://developer.apple.com/documentation/security/updating-mac-software))

### Diagnostics and privacy

- Use unified logging with stable reverse-DNS subsystems and component categories. Apple’s logging system is the native source for Console and `log`, and distribution builds should retain symbol files/archives for crash symbolication. ([Logging](https://developer.apple.com/documentation/os/logging/), [diagnosing with crash reports and logs](https://developer.apple.com/documentation/xcode/diagnosing-issues-using-crash-reports-and-device-logs))
- Do not log document content, raster payloads, filenames, usernames, credentials, or full device/network identifiers. Dynamic strings and complex objects are redacted by default, but numbers are not; mark sensitive interpolated values explicitly private/sensitive or omit them. ([generating log messages](https://developer.apple.com/documentation/os/generating-log-messages-from-your-code), [`OSLogPrivacy`](https://developer.apple.com/documentation/os/oslogprivacy))
- Remote telemetry is not a Gatekeeper prerequisite. Whether to collect it, retain it, request consent, publish a privacy policy, or ship privacy manifests is a product/legal decision. A privacy-preserving baseline is local logs plus an explicit user-generated diagnostic bundle, reviewed before upload.

## Complete uninstall constraints

macOS 26 does not expose a general consumer “reverse this package” operation. Apple’s own examples remove payload files and then separately forget package receipts; `pkgutil --forget` is receipt cleanup, not file removal. Apple’s user guidance likewise says a vendor uninstaller is the best way to remove login items, extensions, and data stored outside an app bundle. ([command-line tools uninstall example](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools), [Apple Support uninstall guidance](https://support.apple.com/102610))

Provide a signed uninstaller/controller that can run while the provider bundle still exists and performs an idempotent sequence:

1. Call `SMAppService.unregister()` and verify the result. The system terminates a running daemon/agent when it unregisters. ([`unregister()`](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister%28%29))
2. Stop/flush product work safely, then remove the signed provider bundle and any product-owned legacy launchd artifacts.
3. Remove only product-owned queues, spool/cache files, logs, configuration, updater state, and authorization-policy entries. Do not delete Apple/CUPS components or unrelated user-created printers.
4. Forget product package receipts after payload removal if the chosen reinstall/upgrade semantics require it.
5. State separately whether user-created settings, history, and diagnostic files are preserved or erased; “uninstall” and “erase my data” need not be the same operation.

Removal may require administrator authorization because the service and its files are system-owned. Even after correct removal, a deleted background item can remain visible in Login Items until macOS’s overnight maintenance clears it; Apple documents this as expected behavior, so immediate disappearance is not a reliable completion test. ([Apple’s package/Service Management sample](https://developer.apple.com/documentation/servicemanagement/updating-your-app-package-installer-to-use-the-new-service-management-api))

## Uncertainties to test on macOS 26

- Whether the actual USB/CUPS path needs a root daemon, a nonroot daemon/account, or only a user agent.
- The exact approval screens and status transitions when a GUI-less package registers its first launch daemon.
- Fresh install, upgrade, duplicate install, and install by one account followed by use from another, as Apple recommends for direct distribution.
- Offline Gatekeeper validation of the stapled package; expired-installer-certificate handling; and update continuity with the same designated requirements.
- Service disabled by the user, non-admin operation, local-network discovery split between daemon and any UI, interrupted jobs, uninstall, and reinstall after complete removal.
- Legacy `/Library/LaunchDaemons` remains recognized, and Apple documents attribution for legacy plists, but current macOS 13+ guidance says to use the bundle-contained structure. Treat legacy support as compatibility, not the design default.
